# Benchmark: Tauri Desktop vs Compose Desktop

Цель — объективное сравнение двух реализаций Linux-клиента перед выбором целевой
(`docs/ROADMAP.md`, решение D1). Suite не меняет бизнес-логику и UI; единственное добавление в код —
`src-tauri/src/bin/kasane-bench.rs`, драйвер, вызывающий существующие `PlayerManager`,
`YouTubeMusicProvider`, `DesktopAudioBackend` без webview (аналог существующих `--smoke`/`--play`
Compose desktop).

## Два уровня измерения

**Уровень A — engine (headless).** Полный стек без окна: каталог/поиск, резолюция потока,
декодирование, очередь, переключение треков, длительная работа. Автоматический, воспроизводимый,
не требует дисплея и подтверждения на запуск GUI. Аудиовывод отключён (mpv `--ao=null`; rodio
открывает устройство, но громкость 0).

**Уровень B — полное GUI.** Запуск реальных окон в текущей сессии: время до окна, idle-ресурсы,
длительная работа UI. Требует явного подтверждения владельца и дисплея. Интерактивные действия
(клики, прокрутка) автоматизируются только при наличии инструмента ввода для Wayland (`ydotool`)
или выполняются вручную по сценарию — в отчёте способ отмечается отдельно.

## Сценарии (одинаковые для обоих)

| ID | Сценарий | Уровень A | Уровень B |
|---|---|---|---|
| S1 | Запуск | время до первого готового вывода драйвера | время до главного окна |
| S2 | Простой | процесс живёт N с без действий | то же с окном |
| S3 | Поиск | `search(query)` × 5, время до результата | через UI — только B |
| S4 | Прокрутка каталога | нет engine-аналога | ручной/ydotool сценарий |
| S5 | Воспроизведение | resolve → `position > 0.5 s`, время до звука | то же через UI |
| S6 | Переключение | `next()` × 5, время до `position > 0.5 s` | то же |
| S7 | Длительная работа | `--play`/`--idle` 20 мин, утечки по тренду PSS | то же с окном |

S4 не существует на уровне A и не подменяется сетевыми операциями. Поиск в Tauri возвращает
только песни (без артистов/альбомов) — это функциональная разница, а не перформанс; в отчёте
фиксируется отдельно, метрики сравниваются как есть.

## Метрики

Сбор — `bench/collect.py`, семплирование дерева процессов по корневому PID каждые 250 мс
(длительный сценарий — 5 с):

- **PSS** суммарно по дереву (`/proc/*/smaps_rollup`, fallback — RSS): текущее, пик, тренд.
- **CPU** % по jiffies дерева: среднее и пик за интервалы «сценарий» и «idle».
- **Время**: холодный запуск (медиана прогонов), search→result, play→audible, next→audible.
- **VRAM**: best-effort — `intel_gpu_top -J`/`radeontop`/`nvidia-smi` если доступны; иначе `NA`
  (не выдумывается).
- **Пиковая память**: max суммарного PSS за сценарий.

В дерево входят все дочерние процессы: `mpv`, WebKitGTK (`WebKitWebProcess`, `WebKitNetworkProcess`),
helper верификатора. Матчинг по PID-родителям, не по имени.

## Воспроизводимость и условия

- Release-сборки: `npx tauri build --no-bundle` → `target/release/kasane`;
  `cd android && ./gradlew :desktop:createDistributable` → `desktop-compose/build/compose/…` и
  `cargo build --release --bin kasane-bench`.
- Одинаковый запрос поиска (`KASANE_BENCH_QUERY`, default «Daft Punk Around the World»),
  одинаковое число повторов (`KASANE_BENCH_REPS`, default 5), тот же трек-источник.
- Сетевые запросы к YouTube идут из обоих клиентов; дисперсия сети — часть измеряемой реальности.
  Прогоны чередуются (Tauri, Compose, Tauri, …) чтобы усреднить дрейф.
- Холодный запуск: между прогонами `sync; echo 3 > drop_caches` не требуется — фиксируется «тёплый»
  кэш ОС для обоих одинаково; первый прогон каждого клиента помечается `cold`.
- Результаты: `bench/results/<timestamp>/{samples/*.jsonl,summary.json,report.md,charts/*.svg}`.
  Отчёт генерируется `bench/report.py` (stdlib only — matplotlib не предполагается).

## Ограничения и асимметрии (не сглаживаются, а фиксируются)

1. Уровень A не измеряет рендеринг, компоновку и отзывчивость UI — для этого уровень B и
   `--render` у Compose (у Tauri аналога нет; единственный сопоставимый GUI-тест — уровень B).
2. **Верификатор Tauri привязан к UI.** В приложении это скрытый WebKitGTK-webview внутри
   процесса; headless такого webview нет. Для сопоставимости `kasane-bench` использует тот же
   standalone WebKitGTK-helper, который поставляет Compose-клиент
   (`KASANE_VERIFIER_HELPER=<kasane-compose --verifier>`, ленивый старт, JSON-lines по stdin).
   Следствия:
   - дерево Tauri-прогона в момент верификации несёт JVM+WebKit (~350–450 МБ), тогда как реальный
     Tauri-клиент несёт только WebKit-процессы своего webview — память Level A у Tauri завышена
     относительно продукта;
   - helper у бенча не имеет idle-таймаута 180 с, как у Compose (`VerifierProcess.idleMs`), поэтому
     в soak он живёт до конца прогона, а у Compose выгружается — медианный PSS soak несопоставим
     напрямую, сравнивать нужно и пик, и состав дерева;
   - трек выбирается первым из резолвящегося (`skipped`-события видны в отчёте); без верификатора
     вообще Tauri на этом хосте не резолвил **ни один** из 20 результатов поиска — engine-уровень
     Tauri без UI не способен воспроизводить, это архитектурная находка, а не артефакт бенча.
2б. **Радио.** Tauri не продлевает очередь похожими треками (у Compose очередь пополняется до
   ~50 после первого трека), поэтому метрики «следующий трек» у Tauri нет: очередь из одного
   трека кончается. Это функциональная разница (`FEATURE_MATRIX.md`), не перформанс.
3. Звук: Compose рендерит через mpv (`--ao=null`), Tauri — через rodio в реальное устройство с
   нулевой громкостью. Цена аудиовывода у Tauri не измеряется на уровне A; это отмечено в отчёте.
4. PSS суммируется по дереву: shared-страницы системных библиотек учитываются пропорционально —
   честная метрика для сравнения, но не «истинное» потребление.
5. Функциональная полнота сравнивается по `docs/FEATURE_MATRIX.md`, а не по производительности.

## Запуск

```sh
bench/run.py build                 # release-сборки обоих
bench/run.py levelA                # S1,S2,S3,S5,S6,S7 headless — автономно, без GUI
bench/run.py levelB                # GUI-сценарии — только после подтверждения владельца
bench/report.py bench/results/<id> # статистика, report.md, SVG-графики
```
