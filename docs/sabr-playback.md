# SABR playback transport

## Implementation

Kasane implements the SABR POST request and incremental UMP response framing in
`provider/sabr`. This is separate from the progressive byte-range DataSource.
Only clear AAC-LC/fMP4 VOD with a consistent segment timeline is currently
supported. Opus/WebM, live broadcasts, encrypted media, partial/compressed media
parts, changing segment grids and server-driven player-response reload are not
implemented. Those cases fail explicitly rather than being passed to a decoder
as ordinary audio.

`HlsPlayerResolver` considers authenticated WEB_REMIX and anonymous IOS responses.
A compatible native HLS manifest retains priority. Otherwise a SABR bootstrap
requires an actual server URL, ustreamer configuration, a clear itag 140 format
and its last-modified identity. Initialization fetches real UMP metadata and the
first media segment on IO before selecting the source.

`TransportMediaSource` feeds an internal, on-demand fMP4 playlist to the existing
Media3 HLS extractor using `SabrDataSource`. The internal `sabr://` URIs contain
no signed CDN parameters. Timing uses server ticks/timescale, including the final
short segment; each fetched segment is checked against that timeline. This is
not a remote HLS URL or an HLS download proxy. No HTTP server is used by production
code. Media3 remains the only player/queue/MediaSession.

The session keeps initialization plus at most four media segments in RAM. Up to 64 segment metadata records are retained separately for transport
acknowledgements, coalesced into contiguous rational-time ranges. Evicting raw
bytes does not erase delivery acknowledgements. An evicted seek target resets
those acknowledgements so it can be fetched again. The real Media3 position is sampled
on the application thread, separate from requested segment start time. The loader
respects server readahead budget instead of advancing a pretend playback clock.
Seek requests fetch the requested time, retaining Media3's queue identity.
Release cancels the active OkHttp call and stops clock sampling. No audio or
signed URLs are written to Room or files.

## Protection and security

The CDN client has no cookie jar, follows no HTTP redirects and automatically
retries no connection. Protocol redirects are restricted to HTTPS googlevideo.com
hosts, the default port and `/videoplayback`; at most two are followed. Cookies,
authentication headers and account secrets are not attached to CDN requests.
The opaque server playback cookie is held only in RAM and returned in the SABR
protobuf context, not an HTTP cookie.

UMP part/response sizes, header counts, segment lengths, format identity, video
identity, context memory and playlist length are bounded. Network exceptions are
replaced with safe fixed messages; diagnostics contain video ID, profile,
position, HTTP status, segment number/bytes and protection status, never URLs.

`StreamProtectionStatus=2` means pending, not permission to invent proof. The low-level diagnostic can consume valid
media while pending. Production source selection requires verified status 1 and
rejects a pending-only bootstrap, so known cold-start media is not offered as a
full-track source. A media-less pending response gets one
bounded pacing retry and is reported as pending, not as a proven refusal.
Status 3 is a terminal attestation rejection. No PoToken
is fabricated, borrowed or generated by bypassing attestation. Kasane currently
has no attestation provider. HTTP 401/403/404/410 and protocol/protection errors
are terminal; temporary IO/server errors use the bounded native load policy.

Protocol field definitions/framing were studied in
[LuanRT/googlevideo](https://github.com/LuanRT/googlevideo), licensed under MIT.
The notice is retained in `third_party/googlevideo-LICENSE.txt` and packaged in
Android assets. No GPL InnerTubeX implementation or dependency was imported.
This does not assign a license to the Kasane project.

## Evidence and limitations

Anonymous host requests for `JALbemLw3G4` returned actual AAC media in UMP. A fast
unpaced probe reached approximately 69.9 seconds, then received no further
media. A separate video-enabled probe explicitly returned protection status 3.
These are network observations, not proof of full playback or proof that pacing
cannot affect the outcome. Real Media3 playback is tested separately.

The synthetic fixture is an original ffmpeg-generated 440 Hz tone, not YouTube
audio. Its server wraps fMP4 in UMP and accepts actual SABR protobuf requests.
It exists only under androidTest; it does not ship in production. JVM tests use
synthetic protocol data and a loopback MockWebServer, with no account credentials.

Build/test results and actual emulator outcomes are recorded below after execution.

### Executed checks

- `assembleDebug testDebugUnitTest assembleRelease assembleDebugAndroidTest
  -PkasaneSabrProbe=true`: passed. 166 JVM tests discovered, 157 passed,
  9 opt-in live tests skipped.
- Isolated AOSP API 35 emulator, `.dev` package, explicit instrumentation runner:
  `SABR MEDIA3 PASSED: full 76.8s, >60s, AAC decoded, EOF, seek back/forward,
  pause/resume, next, queue retained`.
- This fixture proves the SABR/UMP-to-fMP4 Media3 code path, not availability of
  YouTube content or success of Google attestation.

### Real YouTube Media3 outcome after acknowledgement fix

On the isolated emulator, anonymous IOS SABR for `JALbemLw3G4` supplied and decoded
seven real AAC segments. The playback position reached **69,845 ms**. The eighth
segment request and its one bounded retry received HTTP 200 UMP responses with
protection status **2 (pending)** and no further media. Media3 reported code 2000;
the adapter reported `ATTESTATION_PENDING`. The run did **not** reach full-track EOF.
This was paced native playback with the real Media3 clock, not a fast downloader.
No user cookies or fake PoToken were used. An earlier repeated-segment error in
the adapter was fixed by separating transport acknowledgements from raw-byte
cache eviction and coalescing contiguous ranges without millisecond gaps.

The final synthetic SABR fixture was rerun after that fix and again passed full
playback, seek, pause/resume and next/queue checks. The final JVM/build command
passed with 157 tests passed and 9 live tests skipped; `git diff --check` passed.

Full YouTube playback remains unresolved. A compatible legitimate attestation
provider has not been implemented or verified. Status 2 by itself is not a
proven hard rejection, and this report does not claim every SABR stream requires
proof or that cookies alone satisfy it. Status 3 is handled separately as an
explicit rejection. Authenticated WEB_REMIX SABR has not been verified with the
user's account. The new SABR release was not installed on Pixel or pushed as a
completed playback fix. The earlier direct-source-preflight update was installed
in place with certificate verification, without uninstall/clear operations.

## Subsequent bounded web-attestation investigation

A genuine WebView prototype was tested on the isolated API 35 emulator using
BgUtils 4.0.3 (MIT). It did not spoof User-Agent, browser properties or a YouTube
origin. The actual YouTube document refused dynamic interpreter evaluation under
its CSP, which was not weakened. On the honest application origin
`https://appassets.androidplatform.net`, Google's Create/GenerateIT flow returned
an integrity response and the minter produced video-bound proof. This alone is
not proof of GVS acceptance.

An anonymous WEB player request using a fresh server visitor context returned
`UNPLAYABLE` with both session-bound and video-bound player proof. No compatible
SABR bootstrap was obtained, so no GVS acceptance or full-track playback is
claimed for that method. Web proof is never attached to IOS/Android requests.
The remaining signed-in WEB_REMIX check needs a manually authorized emulator
session; the user's Pixel session was not extracted or modified.

The reproduction runner is emulator-only `.dev` instrumentation, explicitly
selected with `-PkasaneProofProbe=true`. Prepare its MIT dependency using
`scripts/prepare-attestation-probe.py`, then build `assembleDebug` and
`assembleDebugAndroidTest` with that flag. Only explicit `adb -s emulator-...`
installation/instrumentation is allowed. The generated JS and public Google
service headers remain under ignored `app/build/`; no API key is committed.
The diagnostic never prints proof, visitor identifiers, cookies or signed URLs.
It is not a configured production attestation provider.

## Core-library verification checkpoint

The subsequent JVM suite contains 191 tests: 182 pass, nine opt-in live tests
are skipped. It covers account-scoped cache isolation, cancellation cleanup,
playlist mutation invalidation without clearing visible content, explicit signed
playlist requests, malformed library responses, and playlist action confirmation.
`PL…` playlist IDs are normalized to `VLPL…` at the browse boundary; existing
`VLLM`/`VL…` IDs are retained. These mock-transport results are not evidence of
successful account reads or writes against a real signed-in YouTube session.

The optional attestation dependency preparation script was executed successfully:
the pinned MIT archive hash matched and the emulator-only bundle was generated
under ignored build output. No generated proof bundle is part of the release APK.
